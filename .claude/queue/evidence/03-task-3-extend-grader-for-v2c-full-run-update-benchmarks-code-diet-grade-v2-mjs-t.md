**Reading this honestly (no tuning applied, per task instruction):**
- CD01/CD02/CD04/CD05/CD06 all show 0/0/0 — the blind labeler (task 2) found
  zero instances of these classes in the 30 real_ai files, and the detector
  also found zero. Precision/recall are the grader's `1.00` default-on-empty
  convention, and the CI is degenerate `[0.00,0.00]` because n=0 — these are
  **not evidence of good performance**, just "no signal either way" on this
  small real-AI sample. This is exactly the kind of under-powered-N case
  EVALUATION.md §5 flags for v2c ("small N on v2c — report CI, mark
  under-powered claims").
- **CD03 precision = 0.00** (13 FP, 1 FN, 0 TP) is the one real signal: on 30
  real AI-generated MCP service files, code-diet's CD03 (unreferenced export)
  detector fired 13 times where the blind labeler did not flag CD03, and
  missed the 1 genuine CD03 the blind labeler did find
  (`vision-mcp/src/artifact-store.ts:16`, `artifactDir()`). This is
  consistent with — not a new bug, but independent confirmation of — the
  already-measured v2a/§5b finding that CD03's "unreferenced-within-corpus"
  heuristic over-fires on legitimate exports it can't see the callers of
  (here: cross-service consumers outside the 30-file blind sample, the same
  "out-of-sample consumer" pattern the task-2 evidence packet already
  flagged as a labeling risk). Per the task instruction, this low number is
  reported as-is; no detector change was made.

## Remaining risks

- v2c's N is small (30 files, 1 blind finding) — the CD03 precision CI is
  wide (`[0.00,0.23]`), and the 5 classes with 0/0/0 carry zero statistical
  power. Any narrative built on top of these numbers (task 4/RESULTS.md) must
  state this, not read "1.00" as "perfect."
- The task-2 evidence packet already notes the blind labeler deliberately did
  *not* flag ~28 "unreferenced-within-sample" exports it judged likely to
  have out-of-sample consumers, to stay conservative. If some of the grader's
  13 CD03 FPs land on exactly those judgment-call files, the "true" precision
  under a stricter/literal blind-labeling rule could differ from 0.00 in
  either direction — this is a labeling-methodology risk already logged in
  task 2's evidence, not something this task's grader change introduces or
  can resolve.
- Per policy, `.claude/queue/current-task.md` and `.claude/queue/status.json`
  are untracked queue-runner bookkeeping files unrelated to this task; they
  were left alone (not staged/committed) here.
